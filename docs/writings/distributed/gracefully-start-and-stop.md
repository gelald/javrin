# 优雅启停

## 什么是优雅启停

在分布式微服务架构下，服务在**关闭**、**重启**、**扩容**和**缩容**的情况下，对业务要尽量做到无损（不能出现大面积的请求 500 Error）

## 需要考虑的问题

最核心的问题：分布式环境中，多个组件对于状态数据的不一致，没有办法做到原子级别的同步，**类似分布式事务，时序很多时候并不可控**，放弃绝对平滑，做到尽量平滑，成本要尽量可控，结合重试/幂等和其他服务治理策略做最后的兜底才是更务实的思路

### 优雅启动的场景

- 启动服务
- K8s 探针探活，**这是应用能接收请求的最基本的必要条件**；但是可能会有数据、缓存需要预热，这里需要考虑如何保证成功，如果服务不是特别核心重要的话，适当延长 startupProbe 的延迟时间，如果服务是核心重要服务，优先考虑把预热工作迁移或者异步，异步后需要埋点 & 日志记录，有失败的情况需要及时介入
- 把服务注册到服务发现上

### 停机的场景

在分布式系统中，已经建立了 RPC 长连接，要怎么去下线一个实例才能尽可能做到对业务无损

- 拒绝新请求，但是会有两个问题
  - 缓存问题：如果直接告诉注册中心，把当前服务 IP 删掉，看起来能满足拒绝新请求，但是现在的注册中心客户端（RPC 服务调用方）会有本地缓存机制，并不会每次请求都会查注册中心服务方的 IP 地址，这些缓存一般会有几十秒的 TTL。这样要保证所有的服务调用方实例的本地缓存都过期，理论上才会没有新请求发送到服务提供方，**本质上也是集群本地缓存一致性的问题**
    - 第一种解决方式是干等，等一轮调用方的本地缓存的 TTL，理论上这么干是可以实现的，但实际生产中没有人会这么做，在分布式系统中进行滚动发布时，如果每一个实例都要等待一个本地缓存 TTL，这个发布周期会变得异常长，发布体验是很很糟糕的；
    - 第二种解决方式是让注册中心发送一个广播消息，告诉服务调用方更新本地缓存，至少把下线的实例地址移除掉，现在主流的注册中心支持这样的操作，但是出于性能方面的考虑，这种消息一般会以异步的方式来广播发送，异步的通知会有新的问题，我们并不知道这个异步通知什么时候完成，等待的时长也取决于网络环境，万一有客户端发生GC或者网络抖动没有收到这个刷新本地缓存的消息或者处理得很慢，就会存在服务下线后，仍然有请求过来，但是这种算是极端场景可以忽略不计，再等待一个TTL的成本是在太高
  - 服务发现问题：K8s Service 和 Nacos 客户端对于服务状态认定的不一致，有可能 K8s 认为这个服务已经终止（摘流），从集群层面这个服务已经下线，但可能在 Nacos 服务端这里实例仍然在线，仍然有新的请求来到应该下线的实例，不同管理组件对于服务发现认知状态的不一致
- 确认存量请求已经处理完毕，Spring提供了优雅关闭的方式，但是对于**定时任务**、**消息消费**、**线程池任务队列**，这三方面的支持是不足的，**需要人工介入处理**
- 清理资源关闭服务

### 发布的场景

蓝绿滚动发布，冗余一套 deployment，发布新版本时把流量切换到新的 deployment
