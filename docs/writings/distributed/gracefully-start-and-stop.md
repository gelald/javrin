# 优雅启停

## 什么是优雅启停

在分布式微服务架构下，服务在**关闭**、**重启**、**扩容**和**缩容**时，对业务要尽量做到无损（不能出现大面积的请求 500 Error）

## 需要考虑的问题

最核心的问题：分布式环境中，多个组件对于状态数据的不一致，没有办法做到原子级别的同步，**类似分布式事务，时序很多时候并不可控**，放弃绝对平滑，做到尽量平滑，成本要尽量可控，结合重试/幂等和其他服务治理策略做最后的兜底才是更务实的思路

- 注册中心服务端的服务列表和注册中心客户端本地缓存的数据不一致问题
- K8s Service 和注册中心服务端对服务健康状况认定的不一致问题

### 启动的场景

- 启动服务
- K8s 探针探活，**这是应用能接收请求的最基本的必要条件**
  > 但是可能会有缓存需要预热、启动回调需要执行，这里需要考虑如何保证成功。如果服务不是特别核心重要的话，适当延长 startupProbe 的延迟时间；如果服务是核心重要服务，优先考虑把预热工作迁移到其他服务上或者异步处理，异步后需要埋点 & 日志记录，有失败的情况需要及时介入
- 把服务注册到注册中心上，提供给其他调用方

### 停机的场景

> 在分布式系统中，服务之间已经建立了 RPC 长连接，要怎么去下线一个实例才能尽可能做到对业务无损

- 拒绝新请求，但是会有两个问题
  - 缓存问题：如果直接告诉注册中心，把当前服务 IP 删掉，看起来能满足拒绝新请求，但是现在的注册中心客户端（RPC 服务调用方）会有本地缓存机制，并不会每次请求都会查注册中心服务方的 IP 地址，这些缓存一般会有几十秒的 TTL。这样要保证所有的服务调用方实例的本地缓存都过期，理论上才会没有新请求发送到服务提供方，**本质上是集群本地缓存一致性的问题**
    - 第一种解决方式是干等，等一轮调用方的本地缓存的 TTL。理论上这么干是可以实现的，但实际生产中没有人会这么做，在分布式系统中进行滚动发布时，如果每一个实例都要等待一个本地缓存 TTL，这个发布周期会变得异常长，发布体验是很很糟糕的；
    - 第二种解决方式是让注册中心发送一个广播消息，告诉服务调用方更新本地缓存。现在主流的注册中心支持这样的操作，但是出于性能方面的考虑，这种消息一般会以异步的方式来广播发送，异步的情况下我们无法确定这个操作什么时候完成，等待的时长也取决于网络环境。最极端的情况是有客户端发生 GC 或者网络抖动没有收到这个更新本地缓存的消息或者处理得很慢，就会存在服务下线后，仍然有请求过来，但这种情况一般可以忽略，因为再等待一个TTL的成本是在太高
  - 服务发现问题：K8s Service 和 Nacos 客户端对于服务健康状态认定的不一致，有可能 K8s 认为这个服务已经终止（摘流），从集群层面这个服务已经下线，但可能在 Nacos 服务端这里实例仍然在线，仍然有新的请求来到应该下线的实例，**这属于是不同组件对于服务发现认知状态的不一致**
- 确认存量请求已经处理完毕，Spring提供了优雅关闭的方式，但是对于**定时任务**、**消息消费**、**线程池任务队列**，这三方面的支持是不足的，**需要人工介入处理**
- 清理资源关闭服务

### 发布的场景

> 对于新版本上线，如何做到平滑切换

- K8s 滚动更新：rolling update 是最常用的方式，按照 pod 的数量逐步替换新服务；流量控制粒度：pod

- Canary 发布 / 灰度发布：新旧版本同时在线，**渐进式切换流量**；流量控制粒度：任意百分比
  - 新旧版本独立部署，`application-v1` 和 `application-v2` 两个独立 Deployment，并且各自有独立的 Service `application-v1-service` 和 `application-v2-service`
  - Kong 里面服务的 Service 的 host 不直接写 K8s Service，而是指定一个 upstream，然后 **upstream 里面指定两个 K8s Service 地址（新旧版本）各自带权重**，pod 扩缩容由 kube-proxy 自动处理
  - 先用 header 路由让内部人员进行测试，Kong 可以配置携带特定 header 的 request 100% 走新版本
  ```yaml
  routes:
  - name: application-canary
    paths: ["/orders"]
    headers: {x-canary: ["true"]}
    service: application-v2-direct   # 带 x-canary 的请求全部进 v2
    ```
  - 内部人员测试完成后，调整不同的权重让小部分用户可以使用新版本，或者**由网关或前端给特定用户（内部账号、某个 region、白名单）注入这个 header**，就从「随机 5%」变成「精确控制谁先用」。期间盯紧**服务错误率**、**核心接口 p99**、**业务指标**等，符合要求再放宽下一个权重
  - 直到 100% 权重后，版本切换完毕，但是旧版本可以先保留 3~5 天，以防有其他未遇见 bug

- 蓝绿发布：**两套完整的环境，一次性全量切换**；流量控制粒度：0 或者 1，没有中间状态，可以看作是 Canary 的特例
  - 部署同一个应用的 `application-bule` 和 `application-green` 两个 Deployment，并且各自有独立的 Service `application-bule-service` 和 `application-green-service`，假设当前需要从蓝切换到绿，所以更新前，`application-bule-service` 承载的是 100% 流量
  - 此时绿色版本上线，先直接调用 `application-green-service` 的 ClusterIP 做**冒烟测试**确保服务正常（只验证服务最核心的路径能不能跑通——服务能启动、不是一上来就坏了那种情况）
  - 在 Kong Gateway 这边把 upstream 从蓝色版本 `application-bule-service` 切换到绿色版本 `application-green-service`，这个操作通常是秒级生效
  - 蓝色版本可以保留，方便出问题时迅速切换 upstream 来回滚
  - 局限点：
    - 窗口期服务器是需要双倍资源的
    - 如果两个版本共用同一个数据库，那么 schema 必须同时兼容两个版本

- **日常可能用 rolling update 为主，高风险变更/框架版本时就用 Canary 或者 蓝绿发布**
